## Context

Новый проект — Telegram-бот для управления VPN-подписками через 3x-ui панель. Кодовая база начинается с нуля. Проект служит одновременно рабочим инструментом и портфолио, поэтому архитектурные решения должны демонстрировать понимание современных практик.

Текущее состояние: существуют клиенты в 3x-ui, управление ведётся вручную через чат. Первая задача — автоматизировать коммуникацию и базовое управление.

## Goals / Non-Goals

**Goals:**
- Зафиксировать стек и архитектурные решения до начала реализации
- Определить модульную структуру проекта с чёткими границами
- Обеспечить масштабируемость: от MVP (без оплаты) к полноценному продукту (оплата, рефералы)
- Создать основу для обучения архитектурным принципам (Hexagonal, CQRS)

**Non-Goals:**
- Детальный дизайн каждого модуля (будет в отдельных changes)
- Выбор платёжного провайдера (v2)
- CI/CD pipeline (будет позже)
- Детальная схема БД (будет при реализации модулей)

## Decisions

### 1. Стек: PHP 8.5 + Symfony 8.0

**Выбор:** PHP 8.5, Symfony 8.0, SergiX44/Nutgram, SQLite + Doctrine ORM, Symfony Messenger + doctrine transport, Docker + docker compose.

**Альтернативы:**
- Python (aiogram) — ниже порог входа, но не в стеке разработчика
- Go — выигрышнее для портфолио, но кривая обучения замедлит MVP
- Node.js (TypeScript) — хороший вариант, но PHP привычнее

**Rationale:** Разработчик пишет на PHP — максимальная скорость при сохранении качества. Symfony обеспечивает enterprise-grade инфраструктуру (DI, Messenger, Doctrine).

### 2. Архитектура: модульный Hexagonal + CQRS

**Выбор:** Модули верхнего уровня (`src/{Module}/`), внутри каждого — `Domain/`, `Application/`, `Infrastructure/`. CQRS через Symfony Messenger bus.

**Структура:**
```
src/
├── User/
│   ├── Domain/          # Entity, Repository (интерфейсы), Event
│   ├── Application/     # Command/, Query/ + Handlers
│   └── Infrastructure/  # Doctrine реализации
├── Subscription/
│   ├── Domain/
│   ├── Application/
│   └── Infrastructure/
├── Panel/               # 3x-ui интеграция
│   ├── Domain/          # Порт (интерфейс клиента)
│   ├── Application/
│   └── Infrastructure/  # HTTP-адаптер
├── Telegram/            # Чистый адаптер, нет Domain
│   ├── Handler/
│   ├── Middleware/
│   └── Keyboard/
└── Notification/
    ├── Domain/
    ├── Application/
    └── Infrastructure/
```

**Альтернативы:**
- Стандартная Symfony структура (`Controller/`, `Service/`, `Entity/`) — проще, но не масштабируется и не учит архитектуре
- DDD-lite верхнеуровневый (`Domain/`, `Application/`, `Infrastructure/` на корне) — менее модульно

**Rationale:** Модуль = bounded context. Каждый модуль самодостаточен. Domain слой имеет 0 зависимостей от фреймворка. Telegram — чистый адаптер без бизнес-логики.

### 3. CQRS через Symfony Messenger

**Выбор:** Все операции (включая синхронные query) идут через bus. Command Bus для записи, Query Bus для чтения.

**Альтернативы:**
- Простые сервисы (`SubscriptionService->approve()`) — меньше файлов, но хуже разделение

**Rationale:** Единообразный подход. Messenger из коробки поддерживает и sync, и async. Легко перевести операцию в async без изменения вызывающего кода.

### 4. БД: SQLite + WAL mode

**Выбор:** SQLite через Doctrine ORM с включённым WAL-режимом.

**Альтернативы:**
- PostgreSQL/MySQL — лучше для конкурентности, но требует отдельный сервис
- Файловое хранилище — слишком примитивно

**Rationale:** Малое количество пользователей. Один файл, простой бэкап, нет внешних зависимостей. WAL mode снимает проблему конкурентных записей при webhook-нагрузке.

### 5. Деплой: Docker + Hetzner VPS

**Выбор:** Docker Compose на отдельной Hetzner VPS. nginx + certbot для HTTPS. Webhook для получения обновлений от Telegram.

**Альтернативы:**
- Голый сервер (php-fpm + nginx) — проще, но не воспроизводимо
- Shared hosting — нет возможности запускать worker процесс

**Rationale:** Docker = воспроизводимость + портфолио. Отдельный от 3x-ui сервер для изоляции.

### 6. Инструкции: Telegraph

**Выбор:** Пошаговые инструкции по настройке VPN публикуются на Telegra.ph. Бот отправляет ссылки.

**Rationale:** Легко обновлять без деплоя. Поддерживает картинки и видео. Чистый UX — одна ссылка вместо серии сообщений.

## Risks / Trade-offs

- **[PHP 8.5 / Symfony 8.0 совместимость]** → Версии за пределами knowledge cutoff. Если Nutgram/Doctrine не поддерживают — откатиться на PHP 8.4 / Symfony 7.x
- **[SQLite под нагрузкой]** → WAL mode решает для малого числа пользователей. Если вырастем — миграция на PostgreSQL через замену адаптера (Hexagonal это позволяет)
- **[Over-engineering для MVP]** → Hexagonal + CQRS добавляет boilerplate. Trade-off принят осознанно: цель — обучение архитектуре
- **[Telegram модуль без Domain]** → Если появится сложная логика маршрутизации — пересмотреть решение
